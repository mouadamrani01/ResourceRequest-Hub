# Windows: MySQL verification before publishing

**Purpose:** Run and understand the full project on Windows before making it public on GitHub. This is a local acceptance procedure, not a production deployment.

## 1. Install the prerequisites

- Docker Desktop for Windows with WSL 2 enabled: <https://www.docker.com/products/docker-desktop/>.
- VS Code: <https://code.visualstudio.com/>.
- Start Docker Desktop before opening the terminal.

## 2. Start the project with MySQL

Open the extracted `ResourceRequest-Hub-Pro` folder in VS Code, open a **PowerShell** terminal and run:

```powershell
docker compose up --build -d --wait
```

Check `http://localhost:8080/login` in your browser. If the page does not load, run `docker compose ps` then `docker compose logs --tail 100` and inspect the error. The first run may download Docker images and can take several minutes.

The Compose setup starts `app` (PHP and Apache), `db` (MySQL 8.4) and `phpmyadmin` (database viewer). The `resource_request_hub` database is created and the tables from `database/schema.sql` are imported automatically when the MySQL data volume is empty. No separate MySQL or phpMyAdmin installation is required.

**View MySQL visually:** open `http://localhost:8081` (phpMyAdmin) and log in with:

- Server: `db` (already selected)
- Username: `resource_app`
- Password: `local_dev_only`

Click the `resource_request_hub` database in the sidebar. The expected tables are `users`, `resource_pools`, `project_spaces`, `resource_requests`, `request_comments`, `request_audit`, `login_throttles`. These credentials are only for local development: never reuse them on an internet-facing server.

Alternatively, inspect the tables from the terminal:

```powershell
docker compose exec db mysql -uresource_app -plocal_dev_only resource_request_hub -e "SHOW TABLES;"
```

Expected tables: `users`, `resource_pools`, `project_spaces`, `resource_requests`, `request_comments`, `request_audit`, `login_throttles`.

## 3. Create two demonstration users

```powershell
docker compose exec -it app php scripts/create_user.php "Demo Admin" admin@example.test admin
docker compose exec -it app php scripts/create_user.php "Demo Member" member@example.test member
```

Each command prompts for a password of at least 12 characters. Use distinct passwords and keep them locally. These accounts have no email-delivery feature and these example email addresses are *not real inboxes*.

Open `http://localhost:8080/login` and sign in as `member@example.test` using the chosen password. Create a project and submit a request for two units from the GPU Research Cluster and check that it appears in the dashboard and stays after refresh. Sign out, sign in as `admin@example.test` and approve it with a comment. Sign back in as the member and verify that its status and history have changed.

## 4. Automated pre-publication checks

In the same PowerShell terminal, run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\verify-before-github.ps1
```

This script does the following:

1. Builds and launches the app, MySQL and phpMyAdmin; checks PHP syntax.
2. Executes the PHP unit tests.
3. Creates a **separate local** MySQL test database called `resource_request_hub_test`, with permission for the development database user.
4. Installs the test database schema.
5. Runs integration checks against real MySQL.
6. Launches a test HTTP server connected to the test database.
7. Runs HTTP smoke tests using a temporary Python container, without installing Python on Windows.

**The integration tests delete test records. Never point them at a real database.** The script checks the `_test` database suffix to minimize mistakes. It does not delete the normal `resource_request_hub` application's data.

If a command fails, **do not publish**. Copy the first error message and correct the problem. The login smoke suite uses test-only accounts generated by the integration script.

## 5. Manual acceptance checklist

Complete all points in [`test-plan.md`](test-plan.md): roles, logout, request lifecycle, history, invalid submissions, filters, unauthorized API access, responsive design. Verify the browser yourself even if all automated tests passed. For API verification, use the browser's developer tools or an HTTP client.

## 6. Inspect the database after your manual test

```powershell
docker compose exec db mysql -uresource_app -plocal_dev_only resource_request_hub -e "SELECT id, title, resource_type, quantity, status FROM resource_requests;"
```

You should see the requests you created. Any status changes should persist after refresh.

## 7. Stop without deleting your data

```powershell
docker compose down
```

Only if you deliberately want to delete **all local demo data** and start over:

```powershell
docker compose down -v
```

The `-v` flag removes the MySQL data volume. Do not use it to stop an application whose data you want to keep.

## 8. Publication gate

Publish the repo only when the automated test script succeeds, the manual test plan passes, secrets are absent from the repository and you understand the system well enough to explain it. Do not confuse local verification with a formal security audit. The repository is intended as a portfolio application, not an internet-facing production service.

This project is independent of RWTH Aachen and the JARDS platform.
